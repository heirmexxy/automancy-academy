Zapier's name for a workflow is a *Zap*. It's the trigger → action → outcome shape from Module 0.1, built from cards in the Zap editor. Each card needs four choices: the *app*, the *event*, the *account* to connect, and the *fields* to fill in.

**4 · text**

```text
*Instant or polling: when does your Zap wake up?*

Remember polling and webhooks from 0.2. Zapier labels triggers that use webhooks as *Instant*: they run within seconds. Other triggers, including Gmail's, *poll*: Zapier checks for new items on a timer. On the free plan that timer is 15 minutes; paid plans check more often.

*What that means for Tolu:* an invoice arriving at 10:02 might be filed at 10:15. For invoices that's fine. For a customer waiting on an order confirmation, you'd want an instant trigger (Modules 1.4 and 2.5).
```

**5 · text**

```text
*Field mapping: fixed text plus data pills*

When you fill in an action's fields, you can type fixed text, insert data from earlier steps, or mix both. Inserted data appears as a small labelled chip, often called a *pill*. At run time, each pill is replaced with that run's real value.

_A file name built from pills and fixed text:_
- *Pill · From Name*: Farmgate Supplies
- *Text*: -
- *Pill · Subject*: Invoice 0192
- *Text*: -
- *Pill · Attachment Name*: inv_0192.pdf

*Nodo:* Every pill is a path into the trigger's JSON from Module 0.3. Zapier just gives the paths friendly names. Watch the type too: a _file_ pill carries the actual file, while a name or link pill is only text.
```

**3 · text**

```text
*Authentication: proving who you are*

In the HTTP Request node, set *Authentication* to either a *predefined credential type* (reuse a credential n8n already knows, such as Google or Slack, for an endpoint its node doesn't cover) or a *generic credential type*:

_The API docs say… · Use generic type · What you fill in_
- "Send `Authorization: Bearer YOUR_KEY`" · Header Auth · Name `Authorization`, value `Bearer sk_live_…`
- "Send header `x-api-key`" · Header Auth · Name `x-api-key`, value: the key
- "Add `?api_key=…` to the URL" · Query Auth · Name `api_key`, value: the key
- "Username and password" · Basic Auth · User and password
- "Register an app, users log in, you get a token" · OAuth2 API · Authorization URL, Access Token URL, Client ID, Client Secret, Scope. Copy n8n's redirect URL into the app's settings.
```

**4 · text**

```text
*Nodo:* If you can see a key in a URL, a header field or a body, it's in the wrong place. Credentials are encrypted, reusable and left out of exports. And with OAuth2, n8n refreshes expiring tokens for you.
```

**5 · text**

```text
*Pagination: getting every page*

APIs return big lists in pages. Read the docs to find which of three styles the API uses:

- *Page number*: `?page=1&per_page=50`, then `page=2`… Usually starts at *1*.
- *Offset / skip*: `?limit=50&skip=0`, then `skip=50`, `skip=100`… Starts at *0*.
- *Next URL or cursor*: The response includes the next page's address or a cursor token: `"next": "https://…?cursor=abc"`. You follow it until it's empty.

The HTTP Request node does this for you under *Options → Pagination*:
```

**6 · text**

```text
- *Mode*: _Update a Parameter in Each Request_ (page number or offset) or _Response Contains Next URL_.
- *$pageCount*: How many pages have been fetched so far, *starting at 0*. Page numbers: `{{ $pageCount + 1 }}`. Offsets: `{{ $pageCount * 50 }}`.
- *$response*: The last response, e.g. `{{ $response.body.next }}` for next-URL APIs.
- *Pagination complete when*: The response is empty, a specific status code arrives, or your own expression is true, such as `{{ $response.body.products.length < 50 }}`.
- *Safety settings*: _Limit Pages Fetched_ (a maximum, so a bug can't loop forever) and _Interval Between Requests_ in milliseconds.
```

**7 · text**

```text
*Rate limits, 429s and retries*

APIs limit how fast you can call them. Go over and they answer `429 Too Many Requests`, often with a `Retry-After` header saying how long to wait. Other temporary failures, such as `500`, `502`, `503` and timeouts, deserve a retry too. A `400` or `401` won't get better if you repeat it.

- *Slow down: pagination*: Set _Interval Between Requests_, e.g. 500 ms for "2 requests per second".
- *Slow down: many items*: When the node runs once per item (100 customers → 100 calls), use _Options → Batching_: items per batch and batch interval.
- *Retry*: In the node's *Settings*: _Retry On Fail_, _Max Tries_ and _Wait Between Tries_.
- *See the limits*: _Options → Response → Include Response Headers and Status_ shows headers like `Retry-After` or `X-RateLimit-Remaining`. _Never Error_ lets you handle error responses yourself with an IF.
```

**32 · quiz** (answer: A)

```text
Which errors are worth retrying automatically?

  A. 429 and 503
  B. 401 and 403
  C. 400 and 404
  D. All of them, forever

Why: 429 (slow down) and 5xx (server trouble) are often temporary. 4xx errors like 401 or 400 need a fix, not a retry.
```
